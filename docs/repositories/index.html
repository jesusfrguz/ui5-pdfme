Modelo común

Cómo funciona

El estudio y el catálogo trabajan con un store común. Cada repositorio adapta su sistema de persistencia al mismo registro de plantilla.

Catálogo / estudio→TemplateStore→memory · localStorage · REST · OData · function

Puedes configurar varios repositorios. El catálogo reúne sus resultados, permite buscar por nombre, descripción y etiquetas, filtra por estado y origen, y conserva repositoryId para saber dónde recuperar o actualizar cada registro. No se eliminan duplicados y, si un origen falla, el listado combinado también falla.

Plantilla en blanco y Cargar PDF están disponibles aunque no haya repositorios. Listar, abrir un registro guardado y persistir cambios sí requieren al menos uno.

Decisión

Qué tipo elegir

TipoAlcanceÚsalo paraNo lo uses para
memoryInstancia actual de JavaScriptDemos, pruebas y registros precargadosConservar cambios tras recargar
localStorageNavegador, origen y perfil actualesPrototipos, trabajo individual y modo localCatálogos compartidos, autorización o grandes volúmenes

Producción multiusuario: usa normalmente REST, OData o function sobre un servicio autorizado. memory y localStorage no proporcionan control de acceso, concurrencia ni una fuente compartida de verdad.
Contrato estable

Registro de plantilla

Todos los proveedores reciben y devuelven la misma forma normalizada. Una respuesta de listado puede omitir template, mapping y dataSources; la respuesta de detalle debe incluir una plantilla pdfme válida.

{
  id: "invoice-es",
  name: "Factura España",
  description: "Factura de ventas aprobada",
  tags: ["ventas", "es"],
  status: "published", // draft | published | archived
  version: "3",
  createdAt: "2026-08-20T09:00:00Z",
  updatedAt: "2026-08-23T10:30:00Z",
  template,
  mapping,
  metadata: { dataContractVersion: "2" },
  dataSources // opcional y desactivado por defecto al guardar
}

Los nombres camelCase y los campos OData habituales (ID, Name, TemplateJson, etc.) se normalizan. Las columnas JSON pueden llegar como objetos o como cadenas JSON. repositoryId lo añade el store y no sustituye al id del registro. Los tres estados son convenciones del catálogo: el backend sigue siendo responsable de validar y autorizar el ciclo de aprobación.

Esquema de backend

Tipos y longitudes de las propiedades

REST mantiene los valores nativos de JSON. OData serializa las etiquetas y los cuatro objetos del documento como texto JSON. version sigue siendo una cadena decimal en el registro JavaScript público y solo se convierte a Edm.Int32 en el límite OData.

El contrato procesable está disponible como JSON Schema y OpenAPI. Las implementaciones de base de datos y OData deben validar el JSON decodificado, no solo la longitud de la columna serializada.

Todas las plataformas

Configuración común

const templateRepositories = [
  {
    id: "session",
    name: "Ejemplos de esta sesión",
    type: "memory",
    records: initialTemplates
  },
  {
    id: "browser",
    name: "Este navegador",
    type: "localStorage",
    storageKey: "my-app.pdf-templates",
    default: true
  }
];

const studio = new WebPdfTemplateStudio("#studio", {
  template,
  templateRepositories
});

id identifica el origen en filtros y llamadas. name es su etiqueta visible. Al guardar sin indicar un origen, se usa el primer repositorio con default: true o, si no existe, el primero de la lista.

React recibe el mismo array en la prop templateRepositories. En UI5, pásalo a configure o llama a setTemplateRepositories.

Volátil

Repositorio memory

templateRepositories: [{
  id: "examples",
  name: "Plantillas de ejemplo",
  type: "memory",
  records: [invoiceRecord, shippingLabelRecord]
}]

El proveedor mantiene records en el objeto de configuración. Al crear asigna un ID y fechas; al actualizar incrementa version. Los cambios desaparecen cuando la aplicación se recarga o se crea otra configuración.

Es la opción más simple para precargar un catálogo reproducible en pruebas y demos. Si los registros iniciales deben conservarse intactos entre instancias, entrega una copia nueva del array.

Navegador

Repositorio localStorage

templateRepositories: [{
  id: "browser",
  name: "Este navegador",
  type: "localStorage",
  storageKey: "my-app.pdf-templates",
  default: true
}]

Guarda el array completo de registros como JSON. La clave predeterminada es ui5-pdfme.templates; usa una clave propia por aplicación y entorno para evitar colisiones. También puedes proporcionar un objeto compatible mediante storage en el repositorio o, en Web, en la configuración del estudio.

Los datos pertenecen al origen y perfil del navegador. Pueden borrarse, tienen cuota limitada, no se sincronizan con otros dispositivos y dos pestañas pueden sobrescribir sus cambios. No trates esta opción como un repositorio corporativo ni como una frontera de seguridad.

Backend JSON

Repositorio REST

templateRepositories: [{
  id: "company-api",
  name: "Plantillas corporativas",
  type: "rest",
  url: "/api/templates",
  headers: { "x-client": "print-studio" },
  maxPages: 50
}]

El contrato predeterminado del adaptador Web es:

OperaciónPetición predeterminadaRespuesta
ListarGET /api/templates?search=&status=&tags=&top=&skip=Array o envoltorio paginado
DetalleGET /api/templates/:idRegistro completo
CrearPOST /api/templatesRegistro guardado
ActualizarPUT /api/templates/:idRegistro guardado

El listado admite un array, { items, total, next }, { items, nextLink }, OData V4 (value/@odata.nextLink) y OData V2 (d.results/d.__next). Se siguen enlaces relativos o absolutos hasta terminar, hasta maxPages (100 por defecto), o hasta desactivar followNext.

En el adaptador Web puedes cambiar nombres de parámetros con searchParameter, statusParameter, tagsParameter, topParameter y skipParameter. Usa getUrl, createMethod, updateMethod, mapRecord y serializeRecord para adaptar una API existente. El proveedor REST nativo de UI5 usa los parámetros fijos search, status, top y skip, y no aplica esas funciones de mapeo.

const repository = {
  id: "legacy-api",
  type: "rest",
  url: "/templates",
  getUrl: (id) => `/templates/${encodeURIComponent(id)}`,
  mapRecord: (payload) => payload.result,
  serializeRecord: (record) => ({ documentTemplate: record })
};

El cliente usa credenciales same-origin por defecto. Para autenticación dinámica, proporciona un fetch de la aplicación; no incrustes bearer tokens en plantillas ni en ejemplos. Valida también el origen de cualquier enlace de página siguiente antes de reenviar cabeceras sensibles.

Documentación y ejemplos: consulta el manual de generación diferida, el ejemplo ejecutable de Node.js y el ejemplo de Docker Compose. Incluyen API REST, worker, persistencia opcional con PostgreSQL, Dockerfile y configuraciones Compose.
V2 / V4

Repositorio OData

JavaScript y React sobre HTTP

templateRepositories: [{
  id: "cap-http",
  type: "odata",
  odataVersion: 4,
  url: "/odata/v4/pdf-templates/Templates",
  fields: {
    template: "TemplateJson",
    mapping: "MappingJson"
  }
}]

Indica odataVersion: 2 para un endpoint HTTP V2; V4 es el valor predeterminado. V4 usa contains, $count=true y PATCH. V2 usa substringof sin tolower para ser compatible con SAP Gateway, $inlinecount=allpages y MERGE; las mayúsculas/minúsculas dependen del backend. Ambos entienden sus envoltorios nativos y siguen la paginación del servidor.

PropiedadCampo OData predeterminado
id, name, descriptionID, Name, Description
tags, status, versionTags, Status, Version
template, mappingTemplateJson, MappingJson
metadata, dataSourcesMetadataJson, DataSourcesJson
createdAt, updatedAtCreatedAt, UpdatedAt

Tags y las columnas terminadas en Json se serializan como cadenas JSON. Los listados seleccionan por defecto solo ID/nombre/descripción/etiquetas/estado/versión/auditoría para dejar los JSON grandes en la petición de detalle; personalízalo con listSelect o desactívalo con false. La lectura conserva ETags V2/V4 dinámicos en record.etag. Para escribir en SAP por HTTP, proporciona un fetch de la aplicación que gestione sesión y X-CSRF-Token, y activa requireEtag: true; después de una respuesta sin cuerpo se relee la entidad para recuperar versión, auditoría y ETag nuevos. fields cambia los nombres usados al filtrar y guardar; si el servicio devuelve nombres completamente distintos, usa REST, function o un proveedor registrado.

SAPUI5 / OpenUI5 / Fiori con modelo propagado

studio.setTemplateRepositories([{
  id: "cap-model",
  name: "CAP",
  type: "odata",
  modelName: "templates",
  path: "/Templates",
  pageSize: 100,
  maxRecords: 10000,
  updateGroupId: "templates"
}]);

Esta modalidad conserva destinos, sesión, CSRF y grupos batch en el modelo de la aplicación. OData V4 usa bindings de lista/contexto y lee páginas hasta agotarlas o alcanzar maxRecords. OData V2 usa read, create y update. Aplica filtros de tenant y propietario en el servicio o en el modelo, no solo en el catálogo.

Selector de implementación SAP: consulta la guía de RAP, CAP, CDS clásico y SAP Gateway/SEGW, con reglas de paquete/transporte, descargas e instalador opcional en modo simulación.
Aplicación

Repositorio function

const repository = {
  id: "application",
  name: "Repositorio de la aplicación",
  type: "function",
  list: (query, context) => templateApi.list(query),
  get: (id, context) => templateApi.get(id),
  save: (record, context) => templateApi.save(record)
};

Las tres funciones pueden ser síncronas o devolver promesas. list debe devolver un array de registros o resúmenes; get devuelve el registro completo; save devuelve la versión persistida. Los callbacks son responsables de los IDs duraderos, fechas, versiones, conflictos y transacciones. Rechaza la promesa para que el estudio emita su evento de error.

Si necesitas reutilizar un tipo propio en varias configuraciones, registra un proveedor. En este contrato el repositorio se recibe como primer argumento:

studio.registerTemplateRepositoryProvider("acme", {
  list: (source, query, context) => {},
  get: (source, id, context) => {},
  save: (source, record, context) => {}
});
Uso

Catálogo, ciclo de vida y API

La primera pulsación en Guardar plantilla solicita nombre, descripción, etiquetas, estado y repositorio. Después, el estudio conserva el registro activo y lo actualiza. Para crear otro registro o versión, guarda metadatos con un id vacío según el flujo de tu aplicación. Cambiar solo repositoryId no mueve ni copia el original.

await studio.listTemplates({
  search: "factura",
  status: "published",
  tags: ["ventas"],
  repositoryId: "company-api"
});

const record = await studio.getTemplateRecord("invoice-es", {
  repositoryId: "company-api"
});
await studio.loadTemplate(record);
await studio.saveTemplateRecord(
  { name: "Factura", tags: ["ventas"], status: "draft" },
  { repositoryId: "company-api" }
);

Catálogo web independiente

import { TemplateStore, WebTemplateCatalog } from "ui5-pdfme";

const store = new TemplateStore(templateRepositories);
const catalog = new WebTemplateCatalog("#catalog", {
  store,
  language: "es",
  onTemplateOpen: ({ template: record }) =>
    studio.applyTemplateRecord(record)
});

React exporta PdfTemplateCatalog y acepta los repositorios en PdfTemplateStudio. UI5 expone setTemplateRepositories, openTemplateCatalog, listTemplates, getTemplateRecord, loadTemplate, saveTemplateRecord y registerTemplateRepositoryProvider. No hay una API común para borrar, mover o consultar un historial de versiones; esas operaciones pertenecen al backend o a la aplicación.

Producción

Seguridad y datos almacenados

Al guardar desde el estudio, dataSources se excluye por defecto. Solo se persiste con persistDataSources: true. Al abrir un registro, las fuentes almacenadas solo se aplican con applyStoredDataSources: true.

const studio = new WebPdfTemplateStudio("#studio", {
  template,
  templateRepositories,
  persistDataSources: false,
  applyStoredDataSources: false
});
  • No guardes tokens, cookies, contraseñas ni payloads privados en template, mapping, metadata o dataSources.
  • Autoriza por separado listar, leer, crear, actualizar y publicar.
  • Impón filtros de tenant/propietario y límites de tamaño en el backend.
  • Valida esquemas pdfme y mapeos antes de publicar.
  • Usa versión o ETag para detectar escrituras concurrentes y conserva versiones publicadas inmutables.
  • Trata nombres, descripciones y etiquetas remotas como texto no confiable.
Checklist

Validar la integración

  • Lista, filtra, abre y guarda en cada repositorio configurado.
  • Comprueba una creación sin ID y una actualización con ID y versión.
  • Verifica que un resumen de listado sin template provoque una lectura de detalle al abrirlo.
  • Prueba paginación relativa y absoluta, el límite configurado y, en Web, la cancelación.
  • Guarda, recarga y genera un PDF válido con el mapeo recuperado.
  • Confirma que fuentes de datos y credenciales no se persisten accidentalmente.
  • Prueba autorización, aislamiento de tenant y conflicto de versión en el backend.

El repositorio incluye un ejemplo REST en Node, un esquema PostgreSQL y un modelo CAP/OData.
