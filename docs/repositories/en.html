Common model

How it works

The studio and catalog use a common store. Each repository adapts its persistence system to the same template-record contract.

Catalog / studio→TemplateStore→memory · localStorage · REST · OData · function

You can configure multiple repositories. The catalog combines their results, searches names, descriptions, and tags, filters by status and source, and preserves repositoryId so it knows where to retrieve or update each record. Results are not deduplicated, and a failed source makes the combined list fail.

Blank template and Load PDF remain available without a repository. Listing, opening a saved record, and persisting changes require at least one.

Stable contract

Template record

Every provider receives and returns the same normalized shape. A list response may omit template, mapping, and dataSources; the detail response must include a valid pdfme template.

{
  id: "invoice-en",
  name: "English invoice",
  description: "Approved sales invoice",
  tags: ["sales", "en"],
  status: "published", // draft | published | archived
  version: "3",
  createdAt: "2026-08-20T09:00:00Z",
  updatedAt: "2026-08-23T10:30:00Z",
  template,
  mapping,
  metadata: { dataContractVersion: "2" },
  dataSources // optional and excluded from saves by default
}

Camel-case names and common OData fields (ID, Name, TemplateJson, and so on) are normalized. JSON columns may arrive as objects or JSON strings. The store adds repositoryId; it does not replace the record's id. The three statuses are catalog conventions: the backend remains responsible for validating and authorizing the approval lifecycle.

Property types and lengths

REST keeps JSON-native values. OData serializes tags and the four document objects as JSON text. version stays a decimal string in the public JavaScript record and is converted to Edm.Int32 only at the OData boundary.

The machine-readable contract is available as JSON Schema and OpenAPI. Database and OData implementations must validate decoded JSON, not only the serialized column length.

All platforms

Common setup

const templateRepositories = [
  {
    id: "session",
    name: "Examples for this session",
    type: "memory",
    records: initialTemplates
  },
  {
    id: "browser",
    name: "This browser",
    type: "localStorage",
    storageKey: "my-app.pdf-templates",
    default: true
  }
];

const studio = new WebPdfTemplateStudio("#studio", {
  template,
  templateRepositories
});

id identifies the source in filters and calls. name is its visible label. When saving without a source, the first repository with default: true is selected, or the first item when none is marked.

React receives the same array in the templateRepositories prop. In UI5, pass it to configure or call setTemplateRepositories.

Volatile

Memory repository

templateRepositories: [{
  id: "examples",
  name: "Example templates",
  type: "memory",
  records: [invoiceRecord, shippingLabelRecord]
}]

The provider keeps records on the configuration object. On create it assigns an ID and timestamps; on update it increments version. Changes disappear when the application reloads or another configuration is created.

This is the simplest option for a reproducible, pre-seeded catalog in tests and demos. If initial records must remain unchanged between instances, provide a fresh copy of the array.

Browser

localStorage repository

templateRepositories: [{
  id: "browser",
  name: "This browser",
  type: "localStorage",
  storageKey: "my-app.pdf-templates",
  default: true
}]

It stores the complete record array as JSON. The default key is ui5-pdfme.templates; use an application- and environment-specific key to avoid collisions. You can also provide a compatible object through storage on the repository or, on Web, on the studio configuration.

Data belongs to the browser's origin and profile. It can be cleared, has a limited quota, is not synchronized to other devices, and two tabs can overwrite each other's changes. Do not treat this option as a corporate repository or a security boundary.

JSON backend

REST repository

templateRepositories: [{
  id: "company-api",
  name: "Company templates",
  type: "rest",
  url: "/api/templates",
  headers: { "x-client": "print-studio" },
  maxPages: 50
}]

The Web adapter's default contract is:

OperationDefault requestResponse
ListGET /api/templates?search=&status=&tags=&top=&skip=Array or paged envelope
DetailGET /api/templates/:idComplete record
CreatePOST /api/templatesSaved record
UpdatePUT /api/templates/:idSaved record

Lists may be an array, { items, total, next }, { items, nextLink }, OData V4 (value/@odata.nextLink), or OData V2 (d.results/d.__next). Relative or absolute next links are followed until exhausted, until maxPages is reached (100 by default), or until followNext is disabled.

In the Web adapter, parameter names can be changed with searchParameter, statusParameter, tagsParameter, topParameter, and skipParameter. Use getUrl, createMethod, updateMethod, mapRecord, and serializeRecord to adapt an existing API. The native UI5 REST provider uses the fixed search, status, top, and skip parameters and does not apply those mapping functions.

const repository = {
  id: "legacy-api",
  type: "rest",
  url: "/templates",
  getUrl: (id) => `/templates/${encodeURIComponent(id)}`,
  mapRecord: (payload) => payload.result,
  serializeRecord: (record) => ({ documentTemplate: record })
};

The client uses same-origin credentials by default. For dynamic authentication, provide an application-owned fetch; do not embed bearer tokens in templates or examples. Also validate the origin of every next-page link before forwarding sensitive headers.

Documentation and examples: read the deferred-generation technical guide, the runnable Node.js example, and the Docker Compose example. They cover the REST API, worker, optional PostgreSQL persistence, Dockerfile, and Compose configurations.
V2 / V4

OData repository

JavaScript and React over HTTP

templateRepositories: [{
  id: "cap-http",
  type: "odata",
  odataVersion: 4,
  url: "/odata/v4/pdf-templates/Templates",
  fields: {
    template: "TemplateJson",
    mapping: "MappingJson"
  }
}]

Set odataVersion: 2 for a V2 HTTP endpoint; V4 is the default. V4 uses contains, $count=true, and PATCH. V2 uses substringof without tolower for SAP Gateway compatibility, $inlinecount=allpages, and MERGE; case sensitivity follows the backend. Both understand their native envelopes and follow server paging.

PropertyDefault OData field
id, name, descriptionID, Name, Description
tags, status, versionTags, Status, Version
template, mappingTemplateJson, MappingJson
metadata, dataSourcesMetadataJson, DataSourcesJson
createdAt, updatedAtCreatedAt, UpdatedAt

Tags and fields ending in Json are serialized as JSON strings. Lists select only ID/name/description/tags/status/version/audit fields by default so large JSON payloads remain in the detail request; customize this with listSelect or set it to false. Reads preserve dynamic V2/V4 ETags in record.etag. For SAP HTTP writes, provide an application fetch wrapper that manages the session and X-CSRF-Token, and enable requireEtag: true; after a bodyless update the entity is reread to obtain its new version, audit values, and ETag. fields changes filtering/saving names; use REST, function, or a registered provider for completely different fields.

SAPUI5 / OpenUI5 / Fiori with a propagated model

studio.setTemplateRepositories([{
  id: "cap-model",
  name: "CAP",
  type: "odata",
  modelName: "templates",
  path: "/Templates",
  pageSize: 100,
  maxRecords: 10000,
  updateGroupId: "templates"
}]);

This mode preserves destinations, session, CSRF handling, and batch groups in the application model. OData V4 uses list/context bindings and reads pages until exhausted or maxRecords is reached. OData V2 uses read, create, and update. Apply tenant and owner filters in the service or model, not only in the catalog.

SAP implementation chooser: see the RAP, CAP, classic CDS and SAP Gateway/SEGW guide, including package/transport rules, downloads and the optional dry-run installer.
Application

Function repository

const repository = {
  id: "application",
  name: "Application repository",
  type: "function",
  list: (query, context) => templateApi.list(query),
  get: (id, context) => templateApi.get(id),
  save: (record, context) => templateApi.save(record)
};

All three functions may be synchronous or return promises. list must return an array of records or summaries; get returns the complete record; save returns the persisted version. The callbacks own durable IDs, timestamps, versions, conflicts, and transactions. Reject the promise so the studio emits its error event.

Register a provider when a custom type needs to be reused across configurations. In this contract, the repository is the first argument:

studio.registerTemplateRepositoryProvider("acme", {
  list: (source, query, context) => {},
  get: (source, id, context) => {},
  save: (source, record, context) => {}
});
Usage

Catalog, lifecycle, and API

The first Save template action requests a name, description, tags, status, and repository. The studio then retains the active record and updates it. To create another record or version, save metadata with an empty id according to your application's workflow. Changing only repositoryId does not move or copy the original.

await studio.listTemplates({
  search: "invoice",
  status: "published",
  tags: ["sales"],
  repositoryId: "company-api"
});

const record = await studio.getTemplateRecord("invoice-en", {
  repositoryId: "company-api"
});
await studio.loadTemplate(record);
await studio.saveTemplateRecord(
  { name: "Invoice", tags: ["sales"], status: "draft" },
  { repositoryId: "company-api" }
);

Standalone web catalog

import { TemplateStore, WebTemplateCatalog } from "ui5-pdfme";

const store = new TemplateStore(templateRepositories);
const catalog = new WebTemplateCatalog("#catalog", {
  store,
  language: "en",
  onTemplateOpen: ({ template: record }) =>
    studio.applyTemplateRecord(record)
});

React exports PdfTemplateCatalog and accepts repositories on PdfTemplateStudio. UI5 exposes setTemplateRepositories, openTemplateCatalog, listTemplates, getTemplateRecord, loadTemplate, saveTemplateRecord, and registerTemplateRepositoryProvider. There is no common API for delete, move, or version-history queries; those operations belong to the backend or application.

Production

Security and stored data

When the studio saves, dataSources is excluded by default. It is persisted only with persistDataSources: true. When opening a record, stored sources are applied only with applyStoredDataSources: true.

const studio = new WebPdfTemplateStudio("#studio", {
  template,
  templateRepositories,
  persistDataSources: false,
  applyStoredDataSources: false
});
  • Do not store tokens, cookies, passwords, or private payloads in template, mapping, metadata, or dataSources.
  • Authorize list, read, create, update, and publish separately.
  • Enforce tenant/owner filters and size limits in the backend.
  • Validate pdfme schemas and mappings before publishing.
  • Use a version or ETag to detect concurrent writes and keep published versions immutable.
  • Treat remote names, descriptions, and tags as untrusted text.
Checklist

Validate the integration

  • List, filter, open, and save in every configured repository.
  • Check a create without an ID and an update with an ID and version.
  • Verify that opening a list summary without template triggers a detail read.
  • Test relative and absolute paging, the configured limit, and, on Web, cancellation.
  • Save, reload, and generate a valid PDF with the retrieved mapping.
  • Confirm that data sources and credentials are not persisted accidentally.
  • Test authorization, tenant isolation, and version conflicts in the backend.

The repository includes a Node REST example, PostgreSQL schema, and CAP/OData model.
