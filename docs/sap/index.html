Qué ruta elegir

Para desarrollo nuevo usa RAP V4 en ABAP moderno o CAP V4 en BTP. Conserva SEGW V2 para paisajes Gateway heredados y CDS clásico solo como índice de lectura.

Recomendado en ABAP

RAP con OData V4

La ruta más rápida soportada es el asistente de ADT Generate ABAP Repository Objects → OData Web API Service. El instalador opcional usa las APIs XCO para crear solo lo que falta: elementos de datos, tabla, vistas raíz/proyección, BDEF, behavior pool, definición y binding de servicio.

El programa toma un paquete transportable y una orden Workbench modificable. Empieza siempre en modo simulación, no sobrescribe ni borra objetos y solo publica el endpoint local cuando se marca expresamente. Está orientado a S/4HANA 2022+; las APIs XCO varían por release/SP, por lo que se debe ejecutar syntax check y ATC en el sistema destino.

Antes de producción: añade DCL/autorizaciones, validaciones del contrato, incremento de versión en servidor, ETag, auditoría read-only y límites. Comprueba que los cuatro JSON aparecen como Edm.String no acotados en $metadata.
BTP

SAP CAP CDS con OData V4

El quickstart CAP Node.js incluido define el esquema, la proyección OData V4, roles TemplateViewer/TemplateEditor, validación, versión/ETag y límites. Usa SQLite en local y documenta la preparación HANA/XSUAA/MTA para BTP.

cd examples/backend/cap
npm ci
npm run start

CAP no usa paquete ABAP ni orden Workbench: sus artefactos viajan por Git, CI/CD, MTA/HDI y la configuración BTP del proyecto.

Legacy por implementar

SAP Gateway / SEGW OData V2

Es la opción heredada capaz de cubrir listado, detalle, alta y modificación con JSON largo, pero el kit no incluye una implementación DPC_EXT. Descarga el EDMX, crea un proyecto SEGW en el paquete/orden del backend, importa el modelo, genera MPC/DPC e implementa la persistencia en DPC_EXT. En SEGW deja Max Length vacío/0 para los cuatro JSON sin límite; estos y Tags deben mapearse a ABAP STRING. El borrado queda fuera del contrato.

  1. Crear/verificar DDIC y proyecto IWPR.
  2. Importar EDMX y generar MPC/MPC_EXT, DPC/DPC_EXT, IWSV e IWMO.
  3. Implementar listado ligero, detalle completo, creación y actualización.
  4. Activar en el hub con alias existente, probar $metadata, CSRF y ETag.

SAP no publica una API universal para crear/importar/generar un proyecto SEGW de extremo a extremo en todos los releases 7.40/7.50. El paso gráfico queda explícito. Para una instalación sin intervención, prepara un transporte o Add-On certificado por release.

Legacy limitado

CDS clásico con autoexposición V2

@OData.publish: true genera el servicio ZPDFME_CDS_TPL_CDS y sus artefactos backend al activar el DDLS; después hay que registrarlo en /IWFND/MAINT_SERVICE o usar el activador opcional del hub.

Esta ruta solo expone ID, nombre, descripción, estado, versión y fechas. Excluye Tags y los cuatro JSON: las vistas CDS DDIC clásicas no admiten de forma portable STRING/RAWSTRING/LCHR/LRAW, y SSTRING no cubre este contrato. Por eso no implementa get/save completo.

Neutral

REST

Si no necesitas metadatos OData, usa el contrato OpenAPI con el ejemplo Node y el esquema PostgreSQL. Es la opción portable para un backend existente y conserva JSON nativo. La autenticación, autorización, aislamiento de tenant, ETag/versión y límites siguen perteneciendo al servicio.

Opcional

Qué hace el instalador XCO

Inventariar→Mostrar plan→Crear faltantes→Validar en SAP
  • Pide ruta RAP/CDS/SEGW, paquete, orden Workbench, Apply y Publish.
  • El modo por defecto solo lista objetos existentes/faltantes.
  • En RAP crea un esqueleto XCO y puede intentar publicar el binding V4 local; no incluye todavía el endurecimiento productivo.
  • En CDS crea un índice V2 de lectura; en SEGW crea DDIC faltante y remite al EDMX, pero no implementa DPC_EXT.
  • No sobrescribe, borra, libera órdenes, crea alias/RFC/trust ni carga datos de catálogo.

Un objeto existente se omite aunque sea incompatible: el informe no compara definiciones. La generación usa varios PUT y no es atómica; revisa el log y compara los objetos con esta guía. Los datos de plantilla son datos de aplicación y no deben transportarse en la orden Workbench.

Consumo

Configuración del cliente

// CAP o RAP V4 por HTTP
{ type: "odata", odataVersion: 4, url: "/odata/v4/.../Templates" }

// Gateway o CDS V2 por HTTP (list/get)
{ type: "odata", odataVersion: 2, url: "/sap/opu/odata/sap/.../Templates" }

El proveedor HTTP evita tolower en filtros SAP V2. Para escribir añade un fetch de la aplicación que gestione sesión y X-CSRF-Token, y usa requireEtag: true con el ETag dinámico leído del registro. En SAPUI5/Fiori prefiere el modelo OData V2/V4 propagado para conservar destino, sesión, CSRF, batches y ETags.

Validación obligatoria

  • Comparar nombres, tipos, nullabilidad y longitudes contra $metadata.
  • Probar lista sin LOB, detalle completo, creación, actualización y conflicto ETag.
  • Probar filtros/paginación V2 o V4 con el cliente elegido.
  • Validar autorización, tenant/propietario, CSRF, tamaño y JSON malformado.
  • Guardar, recargar y generar un PDF válido con la plantilla recuperada.
  • Verificar que ninguna credencial o payload privado entra en plantillas, logs, capturas u órdenes.
