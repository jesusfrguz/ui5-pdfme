Which route to choose

For new development, use RAP V4 on modern ABAP or CAP V4 on BTP. Keep SEGW V2 for legacy Gateway landscapes and classic CDS only as a read-only index.

Recommended on ABAP

RAP with OData V4

The fastest supported path is the ADT Generate ABAP Repository Objects → OData Web API Service wizard. The optional installer uses XCO APIs to create only missing data elements, table, root/projection views, BDEFs, behavior pool, service definition, and service binding.

The program takes a transportable package and a modifiable Workbench request. It starts in dry-run mode, never overwrites or deletes objects, and publishes the local endpoint only when explicitly selected. It targets an SAP S/4HANA 2022+ baseline; XCO APIs vary by release/SP, so syntax-check and ATC-check it in the target system.

Before production: add DCL/authorization, contract validation, server-side version increment, ETag, read-only audit fields, and limits. Confirm that all four JSON fields are unbounded Edm.String properties in $metadata.
BTP

SAP CAP CDS with OData V4

The included CAP Node.js quickstart defines the schema, OData V4 projection, TemplateViewer/TemplateEditor roles, validation, version/ETag handling, and limits. It uses SQLite locally and documents HANA/XSUAA/MTA preparation for BTP.

cd examples/backend/cap
npm ci
npm run start

CAP does not use an ABAP package or Workbench request: artifacts move through Git, CI/CD, MTA/HDI, and the project's BTP configuration.

Legacy implementation required

SAP Gateway / SEGW OData V2

This legacy route can support list, detail, create, and update with long JSON, but the kit does not include a DPC_EXT implementation. Download the EDMX, create a SEGW project in the backend package/request, import the model, generate MPC/DPC, and implement persistence in DPC_EXT. In SEGW leave Max Length blank/0 for the four unbounded JSON fields; these and Tags must map to ABAP STRING. Delete is outside the repository contract.

  1. Create/verify DDIC and the IWPR project.
  2. Import the EDMX and generate MPC/MPC_EXT, DPC/DPC_EXT, IWSV, and IWMO.
  3. Implement a lightweight list, full detail, create, and update.
  4. Activate on the hub with an existing alias; test $metadata, CSRF, and ETag.

SAP does not publish a universal API that creates/imports/generates an end-to-end SEGW project across the 7.40/7.50 landscape. The GUI step remains explicit. For unattended installation, prepare a transport or Add-On certified for each target release.

Limited legacy route

Classic CDS with V2 auto-exposure

@OData.publish: true generates the ZPDFME_CDS_TPL_CDS service and backend artifacts when the DDLS is activated; it must then be registered in /IWFND/MAINT_SERVICE or through the optional hub activator.

This route exposes only ID, name, description, status, version, and dates. It excludes Tags and the four JSON fields: classic DDIC-based CDS views cannot portably expose STRING/RAWSTRING/LCHR/LRAW, and SSTRING cannot cover this contract. It therefore does not implement full-contract get/save.

Neutral

REST

If OData metadata is not useful, use the OpenAPI contract with the Node example and PostgreSQL schema. This is the portable option for an existing backend and preserves native JSON. Authentication, authorization, tenant isolation, ETag/version, and limits still belong to the service.

Optional

What the XCO installer does

Inventory→Show plan→Create missing→Validate in SAP
  • Asks for RAP/CDS/SEGW route, package, Workbench request, Apply, and Publish.
  • The default mode only lists existing/missing objects.
  • For RAP it creates an XCO scaffold and can attempt local V4 binding publication; production hardening is not included.
  • For CDS it creates a read-only V2 index; for SEGW it creates missing DDIC and points to the EDMX, but does not implement DPC_EXT.
  • It never overwrites, deletes, releases requests, creates aliases/RFC/trust, or loads catalog data.

An existing object is skipped even when incompatible: the report does not compare definitions. Generation uses several PUT operations and is not atomic; inspect the log and compare every object with this guide. Template records are application data and must not be transported in the Workbench request.

Consumption

Client configuration

// CAP or RAP V4 over HTTP
{ type: "odata", odataVersion: 4, url: "/odata/v4/.../Templates" }

// Gateway or CDS V2 over HTTP (list/get)
{ type: "odata", odataVersion: 2, url: "/sap/opu/odata/sap/.../Templates" }

The HTTP provider avoids tolower in SAP V2 filters. For writes, add an application fetch wrapper that manages the session and X-CSRF-Token, and use requireEtag: true with the dynamic ETag read from the record. In SAPUI5/Fiori, prefer a propagated V2/V4 OData model for destinations, sessions, CSRF, batches, and ETags.

Required validation

  • Compare names, types, nullability, and lengths against $metadata.
  • Test a LOB-free list, complete detail, create, update, and ETag conflict.
  • Test V2 or V4 filters/paging with the selected client.
  • Validate authorization, tenant/owner, CSRF, size, and malformed JSON.
  • Save, reload, and generate a valid PDF from the retrieved template.
  • Confirm no credential or private payload enters templates, logs, screenshots, or requests.
